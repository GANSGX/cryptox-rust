# Матрица Международных Стандартов Безопасности (`COMPLIANCE_MATRIX.md`)

Этот документ — главный справочник проекта `cryptox-rust` по мировым стандартам криптографии, корпоративных и государственных систем связи. Мы опираемся на эти стандарты, чтобы **не выдумывать велосипеды из головы**, а строить систему, готовую к аудиту спецслужб, банков и крупных корпораций (100 000+ сотрудников).

---

## 1. Стандарты IETF (Инженерный совет Интернета — протоколы мессенджеров)

Именно **IETF RFC** задают математику современных защищенных мессенджеров:

| Код стандарта | Официальное название | Простыми словами: зачем он нужен | Как реализуем в `cryptox-rust` |
| :--- | :--- | :--- | :--- |
| **IETF RFC 9420** | **Messaging Layer Security (MLS) Protocol** | Главный мировой стандарт шифрования корпоративных мессенджеров (разработан IETF при участии Wire, Cisco, Cloudflare, Mozilla, Matrix). Позволяет шифровать как личные чаты (1-на-1), так и гигантские группы (до 50 000+ человек) через дерево ключей **TreeKEM** за $O(\log N)$ вместо медленного $O(N)$. Обеспечивает **Forward Secrecy** (взлом ключа сегодня не раскроет вчерашнюю переписку) и **Post-Compromise Security** (самоисцеление ключей при ротации). | Крейт **`openmls`** внутри клиентского ядра `crates/cryptox-core`. |
| **IETF RFC 9750** | **The MLS Architecture** | Архитектурный стандарт, жестко разделяющий серверную часть мессенджера на два изолированных контура: **Authentication Service (AS)** (удостоверяет личности и ключи) и **Delivery Service (DS)** («слепой» почтальон, который маршрутизирует и хранит зашифрованные пакеты в облаке, физически не имея возможности их расшифровать). | `auth-vault-svc` + `user-directory-svc` играют роль **AS**, а `edge-gateway` + `messaging-svc` играют роль слепого **DS**. |
| **IETF RFC 9807** | **The OPAQUE Asymmetric PAKE Protocol** | Протокол регистрации и входа по паролю/PIN-коду **без передачи пароля на сервер**. Даже во время логина или регистрации сервер не видит пароль ни в открытом, ни в хешированном виде, но при этом клиент получает криптографический ключ для расшифровки своего облачного сейфа (**Encrypted Cloud Key Vault**). | Крейт **`opaque-ke`** в `crates/cryptox-core` и `services/auth-vault-svc`. |
| **IETF RFC 9562** | **UUID Version 7 (Time-Ordered UUIDs)** | Стандарт 128-битных идентификаторов, в первые 48 бит которых зашито время в миллисекундах. Позволяет мгновенно сортировать миллиарды сообщений по времени и делать пагинацию за $O(1)$ без убийственного для БД `OFFSET`. | Крейт **`uuid` (`v7`)** для всех `message_id`, `user_id`, `channel_id`. |
| **IETF Key Transparency** | **Auditable Key Directory (draft-ietf-keytrans)** | Защита от ситуации, когда хакеры или инсайдеры взломали сам сервер мессенджера и пытаются подсунуть Алисе фальшивый публичный ключ Боба (атака Man-in-the-Middle). Все ключи записываются в криптографическое дерево Меркла (как блокчейн-реестр ключей), и клиент автоматически проверяет доказательство (`Merkle Proof`). | Криптографическая верификация версий публичных ключей в `user-directory-svc`. |

## 2. Государственные и Военные Стандарты (Gov / Intelligence / Defense Grade)

Когда мессенджер продается госсектору, оборонке, банкам или объектам критической инфраструктуры, от него требуют соответствия следующим спецификациям:

| Стандарт / Ведомство | Название | Что требует от продукта | Как закрываем в `cryptox-rust` |
| :--- | :--- | :--- | :--- |
| **NSA CNSA 2.0** (АНБ США) & **NIST FIPS 203 / 204** | **Commercial National Security Algorithm Suite 2.0** | Требование к системам уровня национальной безопасности по защите от **квантовых компьютеров** (атака *«Перехвати трафик сейчас — расшифруй через 5 лет на квантовом компьютере»*). Требует использования симметричных ключей не менее 256 бит (`AES-256-GCM`), хешей `SHA-384/512` и перехода на постквантовый обмен ключами (**ML-KEM / Kyber**) и подписи (**ML-DSA / Dilithium**). | Поддержка гибридных постквантовых криптонаборов (`X25519MLKEM768`), 256-битное AEAD-шифрование (`AES-256-GCM` / `ChaCha20-Poly1305`) и `SHA-512` / `BLAKE3`. |
| **NIAP / Common Criteria (ISO/IEC 15408)** | **Protection Profile for Enterprise Communication (PP_APP)** | Международный стандарт сертификации софта для госструктур. Требует: 1) принудительного затирания ключей в оперативной памяти сразу после использования; 2) использования системного аппаратного ГСЧ ОС; 3) хранения локальных ключей в аппаратных модулях (`TPM 2.0 / Secure Enclave`). | Крейт **`zeroize`** (`Zeroizing<T>` на все секреты в RAM), **`OsRng`** для генерации ключей, `SQLCipher` для локальной БД. |
| **NIST SP 800-207** | **Zero Trust Architecture (ZTA)** | Принцип «Никому не доверяй по умолчанию — даже внутри внутренней сети дата-центра». Каждый запрос между клиентом и шлюзом и между микросервисами должен быть криптографически подписан и проверен, а данные разных компаний (`tenant_id`) строго изолированы. | Короткоживущие токены **`PASETO v4`** (`Ed25519`), проверка подписи на `edge-gateway` за микросекунды, обязательный `tenant_id` во всех таблицах. |
| **NIST SP 800-63B** & **BSI TR-02102** (Германия) | **Digital Identity & Cryptographic Mechanisms** | Жесткие требования к деривации ключей из паролей (Memory-Hard KDF для защиты от GPU/ASIC-ферм), длине сессий, MFA и ротации ключей. | **`Argon2id`** (64 МБ RAM, 3 итерации) на стороне клиента для открытия облачного Key Vault + поддержка аппаратных ключей `WebAuthn`. |

## 3. Прикладные стандарты безопасности кода и клиентов (OWASP)

Даже идеальную криптографию можно сломать банальной ошибкой в коде приложения. Поэтому код проверяется по стандартам **OWASP**:

| Стандарт | Уровень | Главные требования к нашему мессенджеру |
| :--- | :--- | :--- |
| **OWASP ASVS v5.0** | **Level 3 (Maximum Assurance — уровень банков и критических систем)** | 1. **V2/V3 (Auth & Session):** Запрет хранения токенов и ключей в `localStorage`. Защита от replay-атак.<br>2. **V5 (Input Validation):** Жесткие лимиты на размер WebSocket/QUIC фреймов, строгая типизация через Protobuf, защита от OOM DDoS.<br>3. **V6 (Cryptography at Rest):** Никаких самописных алгоритмов, принудительная ротация ключей и уникальные 192/96-битные `nonce`.<br>4. **V7 (Error & Logging):** Полный запрет на попадание секретов, паролей, ключей и текста сообщений в логи (`tracing`). |
| **OWASP MASVS** | **MASVS-STORAGE & MASVS-CRYPTO** | На клиентских устройствах (Desktop Tauri v2 / Mobile) криптографическое ядро вынесено из JavaScript/WebView в нативный Rust-процесс (`crates/cryptox-core`), чтобы любая XSS-уязвимость в UI не могла добраться до приватных ключей. |

## 4. Корпоративные стандарты комплаенса (Для продажи B2B Enterprise на 100k+ человек)

Чтобы служба безопасности крупного холдинга или банка разрешила покупку мессенджера, в архитектуру закладываются требования **SOC 2 Type II** и **ISO/IEC 27001**:
1. **Мгновенный отзыв доступа (Instant Offboarding):** При увольнении сотрудника в HR-системе его сессии отзываются за миллисекунды, а в групповых чатах происходит ротация ключа эпохи MLS (`RFC 9420`), чтобы бывший сотрудник не мог прочитать ни одного нового сообщения.
2. **Опциональный корпоративный Key Escrow (HSM компании):** Возможность для компании-заказчика (по ее политике безопасности) хранить резервную копию ключей рабочих чатов, зашифрованную на собственный аппаратный модуль безопасности (HSM) самой компании.
3. **Изоляция отказов и доступность 99.99% (Bulkhead SLA):** Падение модулей поиска, профилей или пушей не останавливает работу основного контура обмена сообщениями.
